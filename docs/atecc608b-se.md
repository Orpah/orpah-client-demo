# ATECC608B 安全元件（c4-γ-2）：接线、命令来源、判据

> 这一步**只做一件事**：把 `payload.nonce` 的来源从**软熵**换成本仓 ATECC608B 的
> `Random(0x1B)`（规范 §5.4 要求 nonce 来自 SE 的 RNG）。
> **签名仍然是软件 P-256 替身** —— Slot0 私钥 / `Sign` / Config 锁 / 产线烧录都是 **d 步**。

## 2. 唤醒与看门狗（这几个数都是**下界**，来自你自己的摘要手册 §2.3 / 表 2-2）

| 参数 | 最小 | 含义 |
|---|---|---|
| `tPU` | 100 µs | 上电后到可以拉 SDA 的时间（"上电自检使能时会**长得多**"） |
| `tWLO` | 60 µs | 把 SDA 拉低这么久（唤醒脉冲） |
| `tWHI` | 1500 µs | SDA 拉高后到可以发数据（**未使能自检**的情形） |
| **`tWHIST`** | **20 ms** | ★ **使能自检**时的同一个等待 ⇒ 这时 1.5 ms 远远不够 |
| `tWATCHDOG` | 0.7 / 1.3 / 1.7 s | 唤醒后这么久没收到**合法命令**就自己回睡 |

★ **`tWHI` 的说明里那句"unless polling is implemented"是救命的**（2026-09-22 逐字核表 2-2 才发现）：
手册**明确允许**用"轮询"代替干等满这个时长 —— 也就是**发一次唤醒令牌、没 ACK 就等一会儿再发**。
我们原来**只等 1700 µs、且只发一次令牌** ⇒ 一颗**完全正常但自检使能**的芯片会一直回 NACK，
现象恰好是「`nack` 逐帧 +1 而 `timeout=0`」（总线全好、器件就是不应答）。
⇒ `Periph/atecc.c` 的 `atecc_wake()` 现在**每轮重做整段序列（脉冲 + tWHI + 令牌）、最多 6 轮**
（标称 ≈21 ms 的忙等，而 `i2c_delay_us()` 实测比标称慢 4~5 倍 ⇒ 真实窗口 ≈85~100 ms，覆盖 20 ms）；
`se` 的判据行会打 `tries=N/6` —— **"第几次才 ACK"就是这颗芯片到底要等多久的实测值**。

⇒ 我们 60 s 才发一条 ID，**每条命令前都必须重新唤醒**（`Periph/atecc.c` 就是这么做的）。
唤醒**不是靠猜时间**：拉完脉冲后发一个"唤醒令牌"（I²C 写地址 `0x00`），**收到 ACK 才算醒** ——
这是 CryptoAuthLib `hal_check_wake()` 的做法。

⚠ 拉低 SDA 那一下必须**先把 I²C 外设关掉**（`i2c_disable()`）：否则外设会把
"SCL 高时 SDA 下降"当成一次 START，后面等 `SB` 就会在错的时刻满足。

## 3. 命令集：我们手上没有 NDA 版手册，用公开实现（**逐条标出处**）

`D:\Downloads\ATECC608B.pdf` 是 **Summary Data Sheet**（28 页），开头就写明
"The complete document is available under NDA" ⇒ **它没有命令集**。所以命令层的事实
取自同厂开源的 CryptoAuthLib（`MicrochipTech/cryptoauthlib`）：

| 事实 | 值 | 出处 |
|---|---|---|
| `Random` 命令码 | `0x1B` | `lib/calib/calib_command.h`（`ATCA_RANDOM`） |
| 模式 | `0x00` 自动更新种子 / `0x01` 不更新 | 同上（`RANDOM_SEED_UPDATE` / `RANDOM_NO_SEED_UPDATE`） |
| 返回数据长度 | 32 B | 同上（`RANDOM_NUM_SIZE`） |
| 无数据命令包长 | `ATCA_CMD_SIZE_MIN` = count+opcode+param1+param2+CRC = **7**（不挂 CRC 时 5） | 同上 + `lib/calib/calib_command.c` 的 `atCalcCrc()` |
| 命令最多耗时 | 23 ms（另一张表 50 ms） | `lib/calib/calib_execution.c` |
| CRC 算法 | ~~poly `0x8005`、初值 0、**MSB-first**~~ ✗ **（2026-10-10 已纠正，见 §8.2 第四段）** 实为：**数据位低位先喂 + 寄存器左移** | `calib_command.c` 的 `atCRC()`：`crc_bit = crc_register >> 15; crc_register <<= 1` 且 `data_bit = (data[counter] & shift_register)`，`shift_register` 从 **0x01** 递增 |
| CRC 线上字节序 | **小端**（低字节在前） | 同上：`crc_le[0] = crc & 0xFF` |
| 响应 count | 32 B 数据的响应 = `ATCA_RSP_SIZE_32` = **35**（这是 CryptoAuthLib 内部计数口径） | `lib/calib/calib_command.h` |
| **I²C 字地址四元表** | `0x00` = **响应（读）**、`0x01` = sleep、`0x02` = idle、`0x03` = **命令（写）** | 见下面 ★★ |

★ 上面那个 CRC ✗ —— **2026-10-10 推翻**：原厂 atCRC 是“数据位低位先喂 + 寄存器左移”的**混合口径**，
**不是** CRC-16/BUYPASS ⇒ 原来那个 “目录校验值 `"123456789" → 0xFEE8`” 的说法**不成立** ✗
（详见 §8.2 第四段；新锚点 = 器件/原厂实回的字节对）
`proto/atecc_cli.c selfcheck` 里 —— 不是"我们自己算的、自己验的"。

## 3b. ★★ 字地址：**命令写 `0x03`、响应读 `0x00`**（2026-09-23 修，真 bug）

我们原先**读写都用 `0x03`** —— 这会让一辈子的命令都读不回响应，而现象**极易误判**：
**地址被 ACK、命令字节写进去了（`tx` 在涨）、但响应一个字节也读不回（`rx=0`）而 `nack` 在涨**
（现场就是这三条同时出现，见 §8）。

正确值从公开实现里能直接读到（**逐条标出处**）：

| 字地址 | 用途 | 出处 |
|---|---|---|
| `0x03` | **命令**（写） | 1 线侧写名：`lib/hal/hal_swi_gpio.h` 的 `ATCA_1WIRE_COMMAND_WORD_ADDR 0x03` |
| `0x00` | **响应**（读） | `lib/calib/calib_execution.c`：非 SWI 设备时 `word_address = 0;` → `atsend(iface, word_address, NULL, 0)`（注释就是 "Send Word address to device..."，只发那一个字节）→ `atreceive(...)` |
| `0x01` | sleep | `hal_i2c_sleep()`：`data[0] = 0x01; // sleep word address value`（多处 HAL） |
| `0x02` | idle | `hal_i2c_idle()`：`data[0] = 0x02; // idle word address value` |

（`0x00` 同时是**唤醒令牌**的地址 —— 两条含义在同一张表里，不矛盾。）

⇒ 现在 `transact()` **两种都试**：先 `0x00`，读不通就**重发一次命令**再试 `0x03`，
并把**哪个通了**记进 `s_st.resp_waddr` —— `se` 会打 `resp_waddr=0x00|0x03|unknown`，
**真机一眼确认，不再靠猜**（和 `crc_mode` 同一套做法）。

## 4. 两处**待上机确认**的假设（写在这里，不要猜）

1. **响应 count 的口径** → ★★ **2026-10-10 结案：`count` 只占 1 字节** ✓（数据从 `resp[1]` 起）
   ⇒ 期望线上读到 **33**（无 CRC）或 **35**（带 CRC）。出处 = 原厂 I²C HAL 的
   `read_length = rxdata[0];`（**只有 TA 器件**才 2 字节）+ 强制件证（唤醒应答**总共只有 4 字节**、
   库里是整体 memcmp 4 字节）✓；`ATCA_RSP_SIZE_32 = 35` 就是**同一个口径** ✓。
   ✗ 我们原来按"4 字节大端 count、响应 36/38"写 —— 那是**把单线的形状套到 I²C 上** ✗
   （器件回的 4 字节错误包因此被算成"长度离谱"，真话 `0xFF` 反而被吃掉 ✗，见 §8.2 第五段）。
   ★ **2026-10-11 上机确认** ✓：`crc_mode=crc(响应 35 B)`、`Random` 取出 32 B ✓。
2. **线上要不要挂 CRC**：取决于芯片 Config 区 `ChipMode` 的 I2C-CRC 位，而我们的摘要手册
   没给这个默认值 ⇒ 不猜：`atecc.c` **先按不挂 CRC 发一条，count 不是 36 再按挂 CRC 发一条**，
   哪一种通就**记住**（`se` 命令会显示 `no-crc(响应 33 B)` 或 `crc(响应 35 B)`）。
   ★★ **2026-10-10：答案 = 要带 CRC** ✓（两个独立证据）：
   · CH347F 侧发**带 CRC 的 7 字节** `Random` 包（`07 1B 00 00 00 6E DD`）⇒ **ACK 计数 = 9 = 全收** ✓；
   · nano 侧发**不带 CRC 的 5 字节**包（`05 1B 00 00 00`）⇒ 地址被 ACK ✓、但**第 3 个字节被 NACK** ✗
     （`tx=20 / nack=21 / nackbyte=3 / timeout=0`）。
   ⇒ ⚠ **固件目前先试 no-CRC、且只在"响应 count 不对"时才换档** ✗ —— 而这里**写就被 NACK 了**
   ⇒ 它永远走不到换档那一步。**这是要改的**（应 CRC 优先 / 把"写被 NACK"也当换档信号）。
   另：带 CRC 时 `count` 字节是 `07`（= 1 opcode + 1 p1 + 2 p2 + 2 CRC + 1 自身），响应期望长度相应变成 **35**
   （= 1 count + 32 数据 + 2 CRC）✓。

  的 I²C 网上** ✓ ⇒ nano 侧的 SDA/SCL 接线与上拉**是通的**。
  ⇒ 剩下的可能只有三种，按这个顺序量：
  ① **SE 到底在不在这条网上**（断电、通断档：nano `PB6` ↔ SE `pin6`、nano `PB7` ↔ SE `pin5`）；

     量 `CH347F.GND ↔ nano.GND` 应 ≈ 0 V）；

  另：CH347F 侧同日测得 `0x60` **双向 ACK**（见 `docs/ch347f-i2c-crosscheck.md` §4b）
  ⇒ "芯片坏了"已排除，别再去怀疑芯片。
- **2026-10-10 稍后（用户把 nano↔SE 那根地线断开后再测）**：`sewake` 读数与上面**逐字相同**
  （`SCL=1 SDA=1`、①/② 两遍扫描都是"无任何器件应答"、`Random` rc=-3）⇒ **断那根地线没改变任何东西**。
  ★ 推论（这正是现在这个组合的形状）：**悬空的地不会让上拉失效** —— 上拉只挂 `3V3↔SDA/SCL`，
  所以两条线照样读到 `1` ✓；而器件自己的参考地若与 nano 不同/悬空，它就**拉不低总线** ⇒
  **永远拿不到 ACK** ✓。⇒ 下一步量四个点（命令见本轮）：

  它从没跟任何"已知好器件"说过话）。⇒ 判定实验：把那两根 I²C 线从 SE 挪到 **CH347F `P5` 的 SDA/SCL**

## 7. 如实边界（别包装成"已支持"）

- **签名不是 SE 做的**：`level=0` 仍是演示级的软件 P-256 ⇒ `se_ok` 仍为 1 的含义
  只是"能做 ES256"，与"SE 在签"**不是一回事**。
- **唤醒脉冲宽度没上示波器**：靠忙等（`i2c_delay_us`，近似、只保证"至少"，
  并且两处约束都是**下界**所以宁可长）；**没有实测过真实宽度**。
- **I²C 时钟假设 APB1 = 8 MHz**（无 PLL、无分频）。改主频/分频要同步改 `Periph/i2c.c`
  里的 `I2C_FREQ_MHZ`，否则会表现为地址 NACK 或读出全 `0xFF`。

## 8. 逐颗验收（2026-09-23）：一颗芯片一行判据

这一轮把**软件侧能自证的都证完了**，SE 仍然**零电气响应**。已排除项（每一条都有可复跑的判据）：

> ⚠⚠ **本节开头这句话当天就被推翻了，保留在此当教训**：真正的现象不是“零电气响应”，
> 而是“**地址被 ACK、命令字节写进去了、响应一个字节也读不回**”（`rx=0` 而 `nack` 在涨）。
> 根因是**我们读响应用错了字地址**（读 `0x00`，我们写了 `0x03`）—— 见 §3b。
> “命令全不过 ⇒ 很可能不是 ATECC”**这条推论已作废**。

| 已排除 | 怎么排除的 |
|---|---|
| 线序 / 哪只脚在哪 | `seline` 把 SCL/SDA 当 GPIO 开漏翻转（**SCL 2 Hz / SDA 1 Hz**）⇒ 逐脚量：`pin6` 快翻转 = SCL 网、`pin5` 慢翻转 = SDA 网、`pin8` = 3.3 V、`pin4` = 0 V，与手册表 1 一致 |
| 供电 | 同上（`pin8` 实测 3.3 V、`pin4` 0 V） |
| 上拉 | 4.7 kΩ ×2 到 3V3（两线静态都是高） |
| 速率 | 100 kHz 与 50 kHz 都试（`seclk`） |
| 唤醒语义 | 改成"轮询 + 最多 6 轮"（§2），仍无 ACK |
| **地址** | `sewake` 扫 `0x01~0x7F`（脉冲前后各一遍）⇒ **没有任何地址 ACK** |
| 驱动层 | 全程 `timeout=0`（没卡在等待里），`nack` 计数与"NACK"一致 |
| 单次 ACK（`0x64`） | ★ **现场只出现过一次**：`sewake` 扫到 `0x64(ACK)`，紧接着 Info/Read/Random 全 NACK。⇒ 判定为**偶然**（见 8.1 第 4 条），不当器件 |

★ 这一轮**真抓出一个固件 bug**（就是这条工装的价值）：`i2c_probe()` 原来**先等 `SB` 再发 START**
⇒ 每次探测都白等到 20 ms 超时 ⇒ `ok` 恒为 0、`nack` 与 `fail` 同步 +1（提交 `b28a78b` 已修）。

### 8.1 一条命令出结论：`sewake`

```
sewake
```

打印（下面示例是"有芯片且未锁"的样子，逐字照 `Periph/atecc.c` 里的格式串）：

```
[sewake] I2C=100 kHz，命令地址当前=0x60
[sewake] 空闲电平：SCL=1 SDA=1（**都该是 1**；有一个是 0 ⇒ 那根线被按住，后面的 ACK 就不一定可信）
[sewake] ① 未脉冲：扫 0x01~0x7F（每址 3 探，≥2 次 ACK 才算）-> 0x35(ACK 3/3, R 3/3) （共 1 个）
[sewake] ★ 器件在 0x35 ⇒ 已把命令地址改成它，接着逐项验：
[sewake] ③ Info(0x30)  -> ok(无CRC)：00 00 60 03   ← 器件版本
[sewake] ④ Read cfg@0x54 -> ok(无CRC)：55 00 00 00   ⇒ **配置区 unlocked（0x55）**
[sewake] ⑤ Random(0x1B) -> ok：前 16 B = …
[sewake] ===== 结论：addr=0x35 rev=ok cfg=unlocked random=OK =====
```

**只看最后那一行**：

| 结论行 | 含义 | 处置 |
|---|---|---|
| `addr=0x00 … random=失败` | 整条总线**没有任何地址**应答 ⇒ 器件侧没反应 | 换下一颗；若颗颗如此，查焊接 / 供电 / 坏件（**"地址写错"已排除**） |
| `addr=0xNN rev=ok cfg=unlocked random=OK` | **这颗能用**（地址 = 0xNN） | 记下 NN：`seaddr NN` 钉住，或把 `i2c.h` 的 `I2C_ADDR_ATECC` 改成它 |
| `… cfg=locked … random=OK` | 别人锁过，但 **`Random` 照样能用**（锁只挡**写**，不挡读/随机） | 本步（γ-2 只要 nonce）**可用**；到 **d 步**要写 Slot0 就必须换颗未锁的 |
| `rev=无`（有地址但读不出信息） | 应答了、但不按 ATECC 协议回 ⇒ 多半是**别的器件占了这个地址** | 记下地址；别当它是可用的 SE |

★ 另外看**空闲电平那一行**：只要有一个是 0 ⇒ 先查那根线（被按住/搭到 GND/虚焊），
**不要**在那种状态下得出\"器件是坏的\"的结论。

★ **单次 ACK（`仅 1/3`）该怎么读**：它证明\"**这条线上确实有东西答过一次**\" ⇒ 连接不是全断，
而是**时通时不通** —— 这正是**虚焊 / 排针接触不良 / 转接板压不紧**的典型签名。
处置：① 重烫那一颗的 8 只脚（尤其 `SDA`/`SCL`/`GND`）；② 再连跑几次 `sewake`：

- 偶发几次、地址还可能变 ⇒ 基本就是焊接/接触问题；
- 每次都稳定同一个地址，但 Info/Read 全 NACK ⇒ 那地址上是**别的器件**（或该芯片已不按 ATECC 协议回）；
- 一次都不再出现 ⇒ 当偶然处理，但先把那 8 只脚补烫一遍再判。

★★ **2026-09-23 当天更新：上面这段里“单次 = 虚焊”的读法被现场推翻了。**
用户随后报告那个 `0x64` 的 ACK **100% 可复现** ⇒ 它不是毛刺，而是**一个稳定应答的东西**。
所以：**“一次 ACK”只能说明“还没测够”** —— 要分清楚必须靠**重复采样**，
这就是下面 `sescan` 存在的原因。
（注：那块板是**当天刚焊好的**；而 100% 复现说明 **“虚焊”这个解释也站不住** ——
成因到现在**仍未查明**，已知仅“答地址、但 `Info(0x30)` 不过”。）

三条实现上的讲究（也在 `Periph/atecc.c` 的注释里）：

1. **扫 `0x01~0x7F`，跳过 `0x00`**：`0x00` 是"唤醒令牌"的写地址，探它会把两种含义混在一起
   —— 而手册第 13 页写明 608B 的 I²C 地址**上锁后可编程**，所以**不能假定 0x60**。
2. **① 命中就不再脉冲**：器件本来就醒着；脉冲是留给"一个都不应答"那种情形的（少一次折腾）。
3. **一个都扫不到时也不早退**：照样在旧地址上写一条命令、**照样打结论行**
   —— ① 万一是探测本身有毛病；② 一颗芯片一行判据，逐颗试的时候不用去分辨"没打结论"是哪种情形。
   （配套：`random_try()` 改成**令牌没 ACK 不早退** —— 器件若已在 Idle，它对 `0x00` 本来就会回 NACK。）
4. ★ **一次 ACK 不算命中（2026-09-23 实测教训）**：现场出现过**仅一次**应答 `0x64`、
   随后 Info/Read/Random 全 NACK。而探针一趟只发一次地址 ⇒ **一次毛刺就能冒充器件**
   （第九个时钟采样到低就是"ACK"，SDA 被按住/线容/噪声都可能造出这一下）。
   现在每个地址**探 3 次、≥2 次 ACK 才算命中**；只 ACK 一两次的会打成
   `[0x64 仅 1/3 ⇒ 偶然，不当器件]` —— **当线索留着看，不当结论**。
   同时先打一行**两线空闲电平**：有一个是 0 ⇒ 那根线被某处按住，
   而这种状态恰好就是"偶然 ACK"的温床（先修线，再谈器件）。
5. ★ **命中那行还带读方向**（`ACK 3/3, R 3/3`）：探针默认发**写**方向（`addr<<1`），
   命中时额外发 3 次**读**方向（`addr<<1 | 1`）。真从机两个方向都该 ACK ⇒
   **`R 0/3` 是"这个 ACK 可疑（不是正常从机）"的一条判据**，且不需要发任何命令。
6. **`se` 会先打一行目标地址**（`[se] 命令发往 addr=0xNN…`）：
   ★ **重烧/复位后 `s_addr` 回到缺省 `0x60`**，而“那颗芯片”在 `0x64` ⇒
   不先 `seaddr 64` 就跑 `se`，得到的是一份**必然失败**的报告（我们 2026-09-23 就这么错过一次）。

### 8.2 其它三条工装

| 命令 | 用途 | 读法 |
|---|---|---|
| `sescan [n]` | **重复扫描统计**：一轮 = 完整唤醒序列 + 扫 `0x01~0x7F`；默认 10 轮、上限 60 | 末几行的表 + 结论行，见下 |
| `seline [1-30]` | SCL/SDA 当 GPIO 开漏翻转 N 秒（**SCL 2 Hz / SDA 1 Hz**）；★ 每拍**读回**实际电平（2026-10-11 加） | 逐脚量：快翻转 = SCL 网、慢翻转 = SDA 网、恒高 = VCC、恒低 = GND、不动 = NC；**读回不一致 ⇒ 有线被顶着**（短路 / 两线互短 / 被别的源拉死）；⚠ **“没接”判不了**（悬空的脚会跟着驱动走）⇒ 那一条仍要万用表量通断 |
| `seclk <khz>` | 运行时改 I²C 时钟（10~400 kHz） | 唤醒令牌必须 ≤ 100 kHz |
| `seaddr <hex>` | 改命令用的 7 位地址 | `sewake` 扫到谁就自动设成谁；也可手动钉住 |
| **`i2crd <a7> <n> [--waddr <h>]`** | **通用读**（2026-10-10 加）：`START+addr\|W+字地址+RESTART+addr\|R+读 n` 字节，n ≤ 32 | 例 `i2crd 50 8 --waddr 0` ⇒ 打 `rc` + 数据 + **本命令的计数器增量**（`tx/rx/nack/timeout/step`）|
| **`i2cwr <a7> <hex…> [--waddr <h>]`** | **通用写**（2026-10-10 加）：`START+addr\|W[+字地址]+数据+STOP` | 例 `i2cwr 50 12 34 --waddr 0` ⇒ 打 `rc` + 增量（24C02 写完要 ~5 ms 再 `i2crd` 读回）|

★ 上面这两条是**2026-10-10 加**的，为的是把"**nano 这条 I²C 主机到底行不行**"变成**可量的**：
在它们之前台架上没有"读任意器件"的手段（`se` 只走 ATECC 专用时序、`sescan` 只探 ACK），
所以"**扫到 ≠ 读得出字节**"这一层一直测不到。标准用法 = 拿 **CH347F-EVT 板载 24C02（`0x50`）**
当已知好器件：`i2crd 50 8 --waddr 0` 出字节、再 `i2cwr` 写进去读回来对得上 ⇒ 主机路就是好的 ✓。
⚠ **不覆盖** AHT20/SHT3x 那种"先写多字节命令、再读"的形状（那要在 `i2c.c` 里另加一段带 RESTART 的
写+读事务）—— 别把它当"传感器全支持"。

★★ **2026-10-10 上机实测（第一次拿真器件把这条主机路跑通）** —— 用
`hardware/wiring/cstep-ch347f-nanoch32-i2ctest` 那张图（目标 = CH347F-EVT 板载 24C02 `0x50`）：

```
[i2crd] addr=0x50 waddr=0x00 n=8 rc=0 数据: ff ff ff ff ff ff ff ff      ← 空白 EEPROM
[i2crd] tx=+1 rx=+8 nack=+0 timeout=+0
[i2cwr] addr=0x50 waddr=0x00 n=2 rc=0                     （tx=+3 nack=+0）
[i2crd] addr=0x50 waddr=0x00 n=2 rc=0 数据: 5a a5         ← **写进去、读回来一致** ✓✓
```

⇒ **nano 的 I²C 主机路（`i2c.c` 的写/读时序 + `PB6/PB7` + 外接 4.7 k 上拉）已证好** ✓
（`nack=0`、`timeout=0`、写后读回逐字节一致）；板载 24C02 的 0/1 两字节现为 `5a a5`
（**故意留的标记**：以后读到 `5a a5` 就说明"还是这颗、还是这次接法"）。
★ 推论：**`se` 报「没应答」不是主机的问题** ⇒ 范围收窄到 SE 那一段（接线/朝向/地址）
或 SE 专用的唤醒/包格式 ✓ —— 下一步最好把 SE 挂到**同一条已验证的线**上两侧交叉看。

★★ **2026-10-10 把 SE 挂到那条"已验证的线"上之后（本轮最重要的两条）**：
- `sewake` ① 未脉冲扫描命中**两个**地址：`0x08` 与 `0x50`（都报 `ACK 3/3, R 3/3`），而 `0x60`
  （ATECC 缺省地址）**不在**其中；固件随即把命令地址切到 `0x08` ⇒ 后面 Info/Read/Random 全失败。
  ⚠ **顺带记一条待改**：`sewake` 命中多个地址时是"选第一个就改地址" ⇒ 它**永远不会去验 `0x60`** ✗ ——
  应当"先按 `s_addr` 试，再把每个命中都验一遍"。
- ★★ **新发现的判据缺陷：`R 3/3`（读方向也 ACK）不是"真器件"的充分证据** ✗ ——
  SDA 被按住 / 被读成低时，**两个方向都会"ACK"**。实测：读路（已被 `0x50` 证明是好的 ✓）去问 `0x08`：
  `i2crd 8 4 --waddr 0` ⇒ **`rc=-2`（超时）**、`tx=+0 rx=+0 nack=+0 timeout=+1 step=3` ⇒
  **地址阶段根本没过去** ⇒ `0x08` 报的 "3/3 ACK" 是**假 ACK** ✓。⇒ 那条"读方向"只能当线索，**不能当判据**。
- **`sescan 2` 的结论是「不稳定」**：轮 1 命中 3 个地址（`0x08`/`0x50`/`0x60`）、轮 2 **命中 0 个** ✗。
  ★ 里面**包括 `0x50`** —— 而 `0x50` 在**没挂 SE 时**是满分的（`i2crd 50 8 --waddr 0` 出 8 B、
  `i2cwr 50 5a a5` 后读回 `5a a5` ✓✓）⇒ 结论：**SE 挂上把整条总线拖得不稳** ✗（连 24C02 都被影响）。
  与 2026-09-23 那次"SE 把总线拖住"的老现象一致 ✓。
- ⇒ 下一步（按代价从小到大）：① **摘掉 SE**，再用 `i2crd 50 8 --waddr 0` 复测 ⇒ 应变回干净 ✓
  （这一步能钉死"就是 SE 那一段"）；② 若确实如此，核 SE 的**朝向**（`pin1` 缺口）、量 `pin8↔pin4`
  应有 3.3 V、`pin4↔GND`、`pin5↔PB7`/`pin6↔PB6` 的**通断**，并看它**烫不烫**
  （供电反接会钳位 + 发热 ⇒ 就是 90 ℃ 那条的老病因）。
- ⚠⚠ **2026-10-10 定案（真因）：SE 的 `SDA`/`SCL` 接反了** ✓（用户自己查出并改正）。
  这一条能解释整串怪现象：反接时 SE 把**错的那根线**往下拉 ⇒ ① 探针看到**假 ACK**（那个 `0x08`

| 表里看到 | 结论行 | 含义 |
|---|---|---|

### 8.12 ★★ 报文层三处口径：**实测**钉死（2026-10-11 晚）
