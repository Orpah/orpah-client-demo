# c3-2b 台架上机记录（CH32V203 模组数据口）

> **结论：✅ 2026-09-21 真机全绿** —— 自家固件在 nanoCH32V203 上跑起来，
> UART2 ↔ TX-AH 的 **HGIC 数据口双向通**（发 `GET_UART_FIXLEN` 收到模组 CMD 应答）。
> 本文件记 **台架怎么接、上电该看到什么、以及四个极难查的真凶** —— 后四条是本文件的主要价值
> （每一个都能让"同一份能跑的源码"变成"灯不亮、串口全静默"）。
>
> ⚠ 本记录只覆盖 **c3-2b**（数据口胶水 + 上机）。选级/签名上报（c4）**未上机**。

---

## 1. 台架（三块板、三根 USB、各自供电、共地）

```
        ┌──────────────┐   UART2 (HGIC 数据口)   ┌────────────┐
        │ nanoCH32V203 │ PA2 ────────────────→ A10│  TX-AH EVB │
        │  (我们的固件) │ PA3 ←──────────────── A11│  (UART 版  │
        │              │                         │   macbus)  │
        │  PA9/PA10 ───┼──→ CH347F P2/UART0 = COM23（控制台）  │
        └──────────────┘                         └────────────┘
                                                      A12/A13
                                                        ↕
                                        CH347F P3/UART1 = COM24（模组 AT/打印口）
```

| 用途 | nano 侧 | 模组侧 | PC 侧 | 备注 |
|---|---|---|---|---|
| **数据口**（HGIC） | `PA2`(USART2_TX) → | `A10`(**模块 RX**) | — | 115200 8N1；`A10`=RX / `A11`=TX 是模组侧**固定**的 |
| | `PA3`(USART2_RX) ← | `A11`(**模块 TX**) | — | |
| **窗口①控制台** | `PA9`/`PA10`(USART1) | — | CH347F **P2/UART0 = COM23** | 自家固件的横幅/命令/统计 |
| **窗口②模组口** | — | `A12`(RX)/`A13`(TX) | CH347F **P3/UART1 = COM24** | 模组的 AT 命令与日志 |

- **心跳灯 = 板载蓝灯 `D1`（`PA15`，低电平点亮），不需要外接线** ——
  依据：原理图 `3V3 → R3(10K) → D1(BLUE) → PA15`，旁证 = 出厂 demo `demo/blink_1000.bin`
  反汇编后驱动的正是 `GPIOA` 掩码 `0x8000`。口径写在 `firmware/Core/board.h` 的 `LED_HEART_*`。
- **不要给模组的数据口（A10/A11）接 AT 命令** —— 那条口跑的是 8 B HGIC 头的二进制帧，
  敲 `AT` 不会有回应；AT/日志在 A12/A13（COM24）。
- ★ **A12/A13 上会看到我们发出的每一帧**（模组把主机口流量也打到打印口）——
  这正是"数据口真的发出去了"的旁证：`[mbus rx] <n> byte(s)`。

## 2. 烧录（**由用户执行**）

1. **BOOT + RST 进刷机态**：按住 `BOOT` → 按一下 `RST` 再松开 → 松开 `BOOT`；
2. WCHISPTool，**下载方式 = USB**，选 `firmware/build/orpah-client.bin`；
3. ⚠ **下载完不会自动运行 —— 必须按一次 `RST`**。
   这一条最容易误判成"固件有问题"：刷完没按 RST 时，板上**什么都不会发生**
   （本项目实测：刷 `orpah-client.bin` 后未按 RST 时"两灯都不亮、COM23 无输出"，
   按 RST 后立刻正常）。

## 3. 上电判据（实测 2026-09-21）

| 观察点 | 期望 |
|---|---|
| 板载 `D1` | 灭 ~0.3 s → **3 下短闪**（"第一口呼吸"）→ 之后 **~1 Hz 心跳**（`BRINGUP_MARKS=0` 时无长闪） |
| COM23 | 横幅 `[orpah-client] CH32V203 firmware ...` + `type 'help'` |
| COM23（每 3 s） | `[mod] tx GET_UART_FIXLEN #N, waiting reply...` |
| COM23（收到应答） | `[mod] ctrl type=3 id=109 status=0 len=2` + `[mod] **DATA PORT IS UP**（模组应答了 GET_UART_FIXLEN）` |
| COM24（每 3 s） | `[mbus rx] 9 byte(s) ...`（= 8 B HGIC 头 + 1 B body）与 `wifimgr host cmd:109` |
| COM24（模组回包） | `[mbus tx] 14 byte(s) ... 6d 00 02 00` + `resp cmd, ret:2` |
| COM23 命令 | `AT` → `OK (rx=N)`；`stat` → 计数器（含 `tick=` / `loops=`）；`help` |

**实测样本（用户粘贴，2026-09-21）**：

```
[mod] tick=16976 loops=...            ← 1 ms 时基在走（中断真的进来了）
[diag] ... t2cnt=85                   ← TIM2 计数在跑
[mod] **DATA PORT IS UP**  ×6         ← 连续 6 次周期探测都有应答（不是一次侥幸）
[mbus rx] ... 6d 00 00 00 → wifimgr host cmd:109
[mbus tx] ... 6d 00 02 00 → resp cmd, ret:2
```

**双向通的判据是"收到 CMD 应答"**，不是"我们写出去了" —— 与 PC 侧
`tools/hgic_bus.py::ping()` 同一口径（写出去只证明串口线连着，应答才证明模组活着且帧层对）。

## 4. ★★ 四个真凶（每一个都表现为"灯不亮、串口全静默"）

排查过程里**每一个**都被先怀疑过别处（工具链/flags/启动文件/ISR 代码生成/波特率/接线），
最后定位到的四个根因如下 —— 都已写进对应源码的注释里：

### ① 链接基址必须是 `0x00000000`（不是 `0x08000000`）

| | |
|---|---|
| 现象 | 镜像烧进去**一条指令都不执行**：灯不亮、串口全静默、按 RST 也没反应 |
| 根因 | CH32V203 的**取指**走低地址区；链接到 `0x08000000` 的镜像不会被执行 |
| 决定性证据 | **同一份源码只差链接基址**的对照：`probe1b.bin`（0x0）→ 两灯闪 + COM23 正常打印；`probe1.bin`（0x08000000）→ 一动不动 |
| 旁证 | WCH 自己的 `EVT/EXAM/SRC/Ld/Link.ld` **三个变体全是** `ORIGIN = 0x00000000`；MounRiver 编出的 `SimulateCDC.hex` 首记录 `:040000006F…` |
| 修法 | `firmware/ld/link.ld`：`FLASH (rx) : ORIGIN = 0x00000000`（注释里写了"别再改回去"） |

### ② `IRQn_Type` 必须带 `+16` 的异常号偏移（= WCH 官方值）

| | |
|---|---|
| 现象 | 所有**中断**都不进来：`tick` 永远 0、串口收不到字节（回显走中断 ⇒ 看着像双向都不通） |
| 根因 | `NVIC_EnableIRQ()` 把传入值**直接当 PFIC 的位号**用。WCH 的 `IRQn_Type` 是**中断号含 16 个异常槽**（`WWDG_IRQn=16 … TIM2_IRQn=44, USART1_IRQn=53, USART2_IRQn=54, DMA1_Channel8_IRQn=62`）；本仓表里原来写的是**外部线号**（28/37/38）⇒ 使能的是错的线 |
| 决定性证据 | 直接读 PFIC 待处理位：`IPR[1]` 的 pending 位**恰好是 53 / 54**（= USART1 / USART2 的官方号）⇒ 外设请求已到 PFIC，只是"使能位写在了别的线上" |
| 修法 | `firmware/Core/ch32v20x.h` 的 `IRQn_Type` 整体 `+16`（含长注释说明症状） |

### ③ `mstatus` 必须写 `0x1888`（MPP=0b11 留在机器模式），不是 WCH 的 `0x88`

| | |
|---|---|
| 现象 | 打成 `0x88`（MPP=0 = 用户模式）时：`main` 里**任何 CSR 访问都会出事**（横幅打完就静默），写 PFIC（`0xE000E000`）**静默失效** ⇒ `NVIC_EnableIRQ` 白写 |
| 根因 | MPP 位的含义：复位后进 `main` 的模式决定了能不能用机器态 CSR / 写 PFIC |
| 修法 | `firmware/startup/startup_ch32v203.S`：`li t0, 0x1888`（MPP=M \| MPIE \| MIE） |

### ④ TIM 的 `INTFR` 是 **write-all-bits**，且 `ATRLR=0` 不产生更新事件

| | |
|---|---|
| 现象 A | 按 STM32 的 `rc_w0` 惯例"写 1 清标志"⇒ **把 `UIF` 又置上** ⇒ ISR 立刻重入 ⇒ **死风暴**，连横幅都打不出来（主循环永远回不去） |
| 现象 B | `ATRLR = 0` 时**根本没有更新事件**（`UIF` 永不置位）⇒ `tick` 不动，看着和"中断没进来"一模一样 |
| 决定性证据 | WCH 官方 `TIM_ClearITPendingBit()` 的写法是 `TIMx->INTFR = (uint16_t)~TIM_IT;`（**不是** `= TIM_IT`） |
| 修法 | `firmware/Core/main.c::tick_init()` / `TIM2_IRQHandler()`：`PSC=7`（1 MHz）、`ATRLR=999`（1 ms）、`CNT=0`、`EGVR=UG`（立刻装载 PSC）、**`INTFR = 0`**（写 0 清零）；ISR 里 `INTFR &= ~UIF` |

## 5. 可复用的排查手法（这次真正管用的几条）

1. **分段闪灯（`BRINGUP_MARKS`）**：每过一个初始化阶段闪 N 下长闪 ⇒ 把
   "固件到底跑没跑"与"哪一步外设初始化失败"分开。灯闪 = 启动/时钟/Flash/GPIO 都好。
   （出厂默认置 0，只留 3 下短闪 + 心跳；下次上机定位再开 1。）
2. **轮询 vs 中断分开发**：串口**回显走中断** ⇒ "没回显"至少有两种成因（中断没进来 /
   字节压根没到芯片）。**轮询 `RXNE` 直接读 `DATAR`** 能把这两件事分开。
3. **直接读 PFIC 待处理位**（`NVIC->IPR[1]`）：区分"请求没离开外设"与"PFIC → CPU 这一段断了"。
   ⚠ **不要用 `NVIC_SetPendingIRQ` 去测电平触发源** —— 软件置位测不出电平源的问题。
4. **对照实验只差一个变量**：① 那条（`probe1` vs `probe1b`）就是靠"同一份源码只差链接基址"
   一次定位的；比"一版一版盲试"快得多（同 AGENTS §0 第 7 条的精神）。
5. **厂商现成产物当交叉证据**：`blink_1000.bin` 反汇编 ⇒ 板载灯就是 `GPIOA` 的 `0x8000`（PA15），
   比翻原理图找网络标号还快。
6. **外设寄存器可写 ≠ 外设有时钟**：`RCC->APB2PCENR |= LED_HEART_CLK;` 这行漏了，
   GPIO 写进去也不会动（灯从 PC13 挪到 PA15 时最容易漏的一处 —— 已收敛成 `board.h` 的宏）。
