#       2026-09-20 取自 https://www.rfc-editor.org/rfc/rfc6979.txt
# 列：<label>	<d>	<h1>	<k>	<r>	<s>   （全部小写十六进制，各 64 字符）
#   label = RFC 里的输入消息（UTF-8）⇒ **h1 必须等于 SHA-256(label 的 UTF-8 字节)**
#           （这一条由 run_cross_test.py 现算核对：抄错 message 也会被抓到）
#   d     = RFC 的私钥 x；它派生的公钥必须等于 RFC 的 Ux/Uy
#           Ux = 60fed4ba255a9d31c961eb74c6356d68c049b8923b61fa6ce669622e60f29fb6
#           Uy = 7903fe1008b8bc99a41ae9e95628bc64f2f1b20c2d7e9f5177a3c294d4462299
#   h1    = SHA-256(message)；qlen=256=hlen ⇒ bits2int 就是"按大端读成整数"，无截断
#   k     = RFC 6979 确定性派生出的 k；r/s = 该 k 下的签名
#
# 为什么**不能**由脚本生成（--refresh 会跳过它）：RFC 给的是确定性 k，而 OpenSSL 的
#   签名接口只吐随机 k 的签名（本机也没有 ecdsa 库）⇒ 这组只能手工录入。
# 那凭什么信它？三条**互相独立**的验证都过才允许改这张表（见 proto/README.md）：
#   ① OpenSSL 验签 (r,s) 通过（证明 r,s 真是 RFC 的值，不是抄串行）
#   ② k 由 (r,s) 反推 —— k = (h + d·r)·s⁻¹ mod n（签名方程保证唯一）——等于表中的 k
#   ③ 本仓**自己的** Python RFC 6979 实现也与表中 k 相等
#   （2026-09-20 实测：①②③ 对两行全部成立；本机没有 ecdsa 库，所以 ③ 是本仓自写的那份）
